# Contract 03 — Prose is not configuration; a changed configuration stays visible

Status: **proposed** (review before any code). Slice 3 of the 2026-09-18 fix plan.
Scope: `lcstatus/evidence.py` (check fingerprint, a frozen alias table, resolution), `lcstatus/rules.py`
(admission split, one new condition state), `lcstatus/render.py` (its label, next action, report),
tests, README "Status rules", and — only once the above has landed — the `note` of
`xapp.accept_ew_to_ip` in `catalogue.json`. No runner changes: runners already record whatever
`check_fingerprint` returns. No product repository.

## Problem (evidence, not description)

- `check_fingerprint` hashes the **whole** check dict (`lcstatus/evidence.py:63-65`), so the free-text
  `note` participates in evidence identity. 28 of 44 checks carry a note; 9 of those are
  `manual_observation` checks whose evidence cannot be regenerated by a tick.
- Admission drops a record whose fingerprint differs from the current one **before** `last_proven` is
  computed (`lcstatus/rules.py:95-101` vs `:130-131`). So editing a note, a claim or any configuration
  makes the condition read **"no evidence"** and the previous pass vanishes. README promises the opposite:
  "A changed configuration or claim remains stale."
- Census on the live store (2026-09-19, 941 records): 21 conditions carry fingerprint-dropped records.
  Dropped **passes with explicit fingerprints** exist for `rel.ip_packaging_checks` (5),
  `rel.ew_linux_desktop_builds`, `bill.cross_app_acceptance` (10, from the two-participant era),
  `rel.ds_linux` (1) and `rel.ip_first_run_model` (1). Every one of those conditions also has admitted
  evidence, so **no label changes today**; the defect is what the *next* edit does.
- The next edit is already queued: the `note` of `xapp.accept_ew_to_ip` still describes the mechanism
  slice 1 replaced. Editing it under today's rule would drop all 48 same-check records to "no evidence".

## Observable behaviour

B1. **Semantic check fingerprint.** `check_fingerprint(check)` hashes the check with its prose keys
removed — exactly `("note",)` — in the same canonical JSON as today. Everything else stays in the hash:
`runner`, `repo`, `platform`, `args`, `paths`, `markers`, `participants`, `job`, `workflow`,
`milestone`, `required_assets`, `desktop_deps`, and `heavy` (it selects which timer produces the
evidence, so it is configuration). `condition_fingerprint` is unchanged: a reworded `proves` is a
changed claim and must invalidate.

B2. **Frozen alias table for fingerprints already written.** A constant
`CHECK_FINGERPRINT_ALIASES: dict[str, str]` in `evidence.py` maps, for every check in the catalogue
**as of the commit that introduces it**, the whole-dict fingerprint to the semantic fingerprint (44
entries; identical pairs for the 16 note-less checks). `resolve_check_fingerprint(value)` returns the
alias's semantic twin for a known whole-dict value and the value itself otherwise. Admission compares
`resolve_check_fingerprint(record_check_fingerprint(r)) == check_fingerprint(current check)`. The
table is generated once, by the same canonical functions, from the catalogue **before** any note edit
in the same change, and is committed as data — the same shape as `LEGACY_CHECK_FINGERPRINTS`.

B3. **Legacy prefix composition is unchanged.** The 151-row authenticated prefix keeps receiving
`LEGACY_CHECK_FINGERPRINTS` values in memory exactly as today; those values then pass through the same
resolution. A prefix row whose check is byte-identical to the catalogue at the freeze therefore stays
admitted; one whose check changed since c482727 stays excluded, as today. Fingerprint-free rows outside
the prefix (91 rows at positions 153–261) stay excluded: they cannot be attributed to any configuration.

B4. **A changed configuration or claim stays visible.** When a condition has **no admitted evidence**,
records that match its id, kind and check but fail fingerprint resolution (a different configuration
or a different claim) and include at least one `pass` yield the new state `config_changed`, with
`last_proven` = the latest such pass, ordered as `changed_since` orders. Admitted evidence always takes
precedence: one admitted record of any verdict routes the condition through today's tree.

B5. **What `config_changed` means downstream.** Condition label "configuration changed since
verification"; task freshness treats it as `changed_since_verification`; next action
"Re-verify under the current configuration (<check>): <proves>", ranked between `changed_since` and
`not_checked`; the report shows the historical pass with its revision and date. It is **not** a proving
state: it never satisfies, never counts toward `partly built` (a pass under a different configuration
or claim proves nothing about this one), never counts as current, and never clears a release gate.

B6. **Runners and the observation script are unchanged** and start writing semantic fingerprints
automatically (`Runner._source` and `record_observation.py` both call `check_fingerprint`).

B7. **README "Status rules"** states: prose notes are not configuration; a changed configuration or
claim reads "configuration changed since verification" until re-verified under the current one;
fingerprint-free rows outside the authenticated prefix stay excluded.

B8. **Demonstration edit.** In a separate commit after the code, the `note` of `xapp.accept_ew_to_ip` is
rewritten to describe slice 1's mechanism. Under B1+B2 this changes no fingerprint that any record is
compared against, so every one of that check's records stays admitted.

## Invariants

I1. Evidence is never rewritten; the store stays append-only.
I2. **No record admitted today is un-admitted by this slice**, for any condition: the alias table
covers every whole-dict fingerprint the current catalogue can produce, and legacy composition is
unchanged (B3). Verified on the real store (settling evidence, live).
I3. Every non-prose edit still invalidates exactly as today; only `note` edits become free.
I4. `config_changed` is visible but never proving (B5).
I5. The alias table is frozen data, generated once; it is never recomputed from a later catalogue
(that would re-bind old fingerprints to edited configurations).

## Failure cases

| Situation | Result |
|---|---|
| note edited on a check with whole-dict-fingerprinted records | records resolve through the alias to the unchanged semantic fingerprint → still admitted |
| note edited on a check with semantic-fingerprinted records | semantic fingerprint unchanged → still admitted |
| `args`/`paths`/`participants`/… edited | old records fail resolution → `config_changed` if any passed and nothing is admitted, else `no_evidence`; next tick re-verifies automated checks; manual demos stay `config_changed` until re-recorded |
| `proves` reworded | same as above (claim changed) |
| a record with an unknown fingerprint (neither alias key nor current) | fails resolution, as today |
| fingerprint-free row outside the prefix | excluded, as today (never `config_changed`) |
| condition with admitted evidence and also mismatched passes | admitted evidence decides; mismatched passes are ignored, as today |

## Concurrency model

None: pure functions over the loaded store; fingerprints are computed at write time by whichever
process writes (collector under `data/.lock`, observation script).

## Decisions

D1. **Alias table instead of "accept either the semantic or the current whole-dict fingerprint".**
The latter breaks on the first note edit for every record written before the slice — including the
nine manual-demo checks that cannot be re-run. The frozen table keeps them valid across any number of
future note edits and is the pattern the code already uses for the legacy prefix.
D2. **`config_changed` replaces only `no_evidence`.** A pass under another configuration must never
outrank evidence gathered under the current one; it is history, shown as history.
D3. **`heavy` stays in the fingerprint.** It changes which timer produces the evidence; excluding it
would let a routine result stand in for a heavy one after a flag flip.
D4. **The note edit ships in the same PR, as its own commit after the code**, because it is the
slice's live proof: a prose edit that visibly changes nothing.
